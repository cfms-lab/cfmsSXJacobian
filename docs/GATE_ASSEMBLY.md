# 조립 게이트 — 암시적 단계가 실제로 쓰는 것만 조립한다

속도 게이트(`docs/GATE_SPEED.md`) 뒤 병목은 조립이다. 지금의 `AssembleConditionForce` 는 힘 두 개와 12 × 12
조밀 행렬 셋(`K` · `∂d/∂x` · `∂d/∂v`, 432 성분, 약 3.5 KB)을 힌지마다 채워 힌지당 약 300 ns 가 들고, 단계판 평가
(약 390 ns)와 맞먹는다.

판정 기준은 실행 전에 고정한다(볼트 규칙 §1, 2026-11-12).

## 방법 — 원문 식 (6) 이 쓰는 꼴로 바로 모은다

원문의 backward Euler 한 단계는 식 (6) 에 `M` 을 곱한 선형계다.

```
(M − h ∂f/∂v − h² ∂f/∂x) Δv = h (f₀ + h ∂f/∂x v₀)
```

풀이기가 쓰는 것은 요소마다 **행렬 기여 `A = −h ∂f/∂v − h² ∂f/∂x`** 와 **우변 기여 `b = h(f + h ∂f/∂x v)`** 뿐이다.
조건 하나에서 식 (7) · (8) · (11) · (12)(비대칭 항을 버린 원문 꼴)를 넣으면

```
A = (h·kd + h²·k) ∇C∇Cᵀ + h²(k·C + kd·Ċ) ∇²C                    대칭 → 위 삼각 78 개
b = −h(k·C + kd·Ċ) ∇C − h²[ k·Ċ ∇C + (k·C + kd·Ċ) ∇²C v ]       12 개
```

로 계수 두 개와 `∇C · ∇²C` 만으로 정리된다. `K` · `∂d/∂x` · `∂d/∂v` 를 따로 만들지 않는다. 새 함수
`AssembleImplicit`(`src/sx_condition_force.h`)는 `A`(위 삼각) · `b` · 전체 힘 `f + d` 를 낸다. 기존
`AssembleConditionForce` 는 그대로 둔다(비대칭 항을 남기는 꼴과 각 행렬을 따로 보고 싶을 때).

## 명제

| | 명제 |
|---|---|
| R1 | `AssembleImplicit` 가 기존 조립에서 만든 `A` · `b` · 힘과 반올림 수준에서 같다 |
| R2 | 기존 조립의 `K` 자체가 맞다 — 착수 게이트 G3 은 `∂d/∂x` 만 유한차분으로 확인했으므로, 기준을 쓰기 전에 `K` 를 탄성력의 유한차분과 견준다 |
| R3 | 조립 비용이 기존의 1/3 이하다 |

## 판정 기준 (실행 전 고정 · 2026-11-12)

상대오차 = 힌지마다 `max|Δ| / max|기준|`, 표본 전체의 최댓값. 계수는 `k = 1`, `kd = 0.1`, `h = 0.01 s`
(원문 인체 위 의복의 대표 단계 0.02 s 와 같은 자릿수). 힌지 · 속도는 `results/hinges.txt`.

| 게이트 | 기준 | 표본 |
|---|---|---|
| R1 `A` · `b` · 힘 (단계판 `EvalStaged` 위에서) | 상대오차 ≤ 1e-13 | 1000 개 |
| R2 기존 `K` 대 탄성력 `f = −k C ∇C` 의 중심차분(간격 = 변 길이 × 1e-6, 분모 = 실제 간격) | 상대오차 ≤ 1e-6 | 1000 개 |
| R3 시간 | `ns(평가 + 새 조립) − ns(평가) ≤ [ns(평가 + 기존 조립) − ns(평가)] / 3` | 격자 힌지 118,405 개, SXMesh 에서 모으기 포함, 단일 스레드, 5 회 중 최소, 평가 = `EvalStaged` |

**R1 – R3 를 모두 통과하면 GO.**

조립 시간에 넣는 것: 기존은 `f + d` 를 노드로 흩뿌린다(속도 게이트와 같다). 새것은 `b` 와 `f + d` 를 흩뿌린다.
둘 다 행렬을 전역 희소 행렬로 흩뿌리는 비용은 넣지 않는다 — 엔진의 저장 방식에 달린 것이라 이 게이트 밖이다.

1/3 로 정한 이유: 행렬 성분 수가 432 → 78 로 5.5 배 줄고 쓰는 메모리도 그만큼 준다. 1/3 은 그 이득의 대부분이
실제로 시간에 나타나는지 보는 선이다.

## 2 차 시도 — 생성기가 평가와 조립을 한 함수로 낸다 (실행 전 고정 · 2026-11-12)

**기준은 1 차와 같다. 바뀌는 것은 구현뿐이다.** 2 차에서도 R3 에 못 미치면 이 게이트는 NO-GO 로 닫고, 1 차 함수의
채택 여부를 사용자가 정한다(3 차 시도는 하지 않는다).

방법: 생성기가 `EvalImplicit(x, ev, v, prm = {k, kd, h}) → C, f + d, A(위 삼각), b` 를 더 낸다. `∇C` · `∇²C` 를 배열로
쓰지 않고 지역 값으로 바로 쓴다. 그리고 단계 구조를 써서 우변의 `∇²C v` 를 행렬 곱 없이 얻는다.

```
u̇ = J v                                   (중간 변수의 속도, J 희소)
Ċ = ∇ᵤC · u̇
∇²ₓC v = Jᵀ (∇²ᵤC u̇) + Σₖ (∂C/∂uₖ)(∇²ₓuₖ v)   (∇²ₓuₖ 는 상수 희소)
```

1 차의 `∇²C v`(위 삼각에서 144 곱셈)가 9 × 9 곱 하나와 희소 곱 둘로 바뀐다. `A = α∇C∇Cᵀ + β∇²C`, `b`, 힘은 1 차와 같은 식이다.

| 게이트 | 기준 (1 차와 같음) |
|---|---|
| R1′ `EvalImplicit` 의 `A` · `b` · 힘 대 기존 조립에서 만든 기준 | 상대오차 ≤ 1e-13, 1000 개 |
| R2 기존 `K` 대 탄성력 유한차분 | 상대오차 ≤ 1e-6, 1000 개 (1 차와 같은 시험) |
| R3′ 시간 | `ns(EvalImplicit + b · f 흩뿌리기) − ns(EvalStaged) ≤ [ns(EvalStaged + 기존 조립 + f+d 흩뿌리기) − ns(EvalStaged)] / 3`, 같은 번역 단위 · 같은 실행 · 5 회 중 최소 |
| 보고만 | 1 차 `AssembleImplicit` 의 비, 압축 명세의 `EvalImplicit`, 생성 연산 수 |

`EvalStaged` · `Eval` · `EvalFrozen` 의 생성 결과는 바뀌지 않아야 한다(S3 와 같은 방식으로 함수 본문 SHA-256 을 확인한다).

### 구현에서 바꾼 것 (2 차 시간을 재기 전, 연산 수만 보고 · 기준은 그대로)

위 방법의 「`∇²C v` 를 단계 구조로」는 셈이 틀렸다. 명세의 희소 구조를 세면(J 의 기호 성분 36 · 상수 ±1 성분 6,
`∇²ₓuₖ` 의 0 아닌 성분 72 개가 모두 ±1) 단계 경로는 `u̇ = Jv` 36 + `K′u̇` 81 + `Jᵀ(·)` 36 + `G′·(∇²ₓu v)` 36 = 곱셈 189 개이고,
`A` 의 위 삼각에서 바로 `A v` 를 만들면 144 개다. 그래서 다음 꼴로 낸다(대수적으로 같다).

```
K′ = α ∇ᵤC∇ᵤCᵀ + β ∇²ᵤC,   G′ = β ∇ᵤC            (중간 변수 공간 9 × 9, α = h·kd + h²k, β = h²(kC + kd·Ċ))
A  = Jᵀ K′ J + Σₖ G′ₖ ∇²ₓuₖ                      (= α∇C∇Cᵀ + β∇²C, EvalStaged 의 H 와 같은 길을 K′ · G′ 로 돈다)
f  = −(kC + kd·Ċ) ∇C
b  = −h k C ∇C − A v                             (b + A v = h(f + d) − h ∂d/∂v v = h · 탄성력 이므로)
```

`α∇C∇Cᵀ + β∇²C` 를 좌표 공간 78 성분에서 곱하던 것(곱셈 168)이 중간 변수 공간 45 성분(곱셈 108)으로 옮겨진다.
생성 연산 수(SymPy `count_ops`): `EvalStaged` 2752 → `EvalImplicit` 3253(+501), 압축 명세 1713 → 2214(+501).

### 측정 방법 변경 (R3′ 를 재기 전 · 기준식은 그대로)

첫 빌드에서 `EvalImplicit` 를 헤더에 더한 것만으로 속도 게이트의 `EvalStaged` 가 386 → 661 ns 로 바뀌었고,
원인은 실행 파일이 **놓인 곳**(로드 주소 등)이었다(같은 기계어, 함수 하나만 1.6 – 3.3 배 느려짐. 경위 · 근거는
`docs/GATE_SPEED.md` 「측정 방법 변경」). 「같은 번역 단위 · 같은 실행 · 5 회 중 최소」로는 이것이 없어지지 않는다.
R3′ 는 차 `ns(EvalImplicit …) − ns(EvalStaged)` 로 재므로, `EvalStaged` 만 늦게 놓이면 판정이 거짓으로 유리해진다.

그래서 R3′ 의 시간은 `tests/timing_bases.py` 가 **고정 로드 주소 8 곳에서 잰 값의 변형별 최솟값**으로 모은다(각 주소에서는
같은 exe 안 5 회 중 최소). 기준식은 위 표 그대로다. 1 차의 비도 같은 방법으로 다시 내되 보고만 한다(1 차 판정 NO-GO 는
그때의 방법으로 내린 것으로 남긴다). 1 차 결과 절의 「번역 단위마다 컴파일러가 다르게 짰다」는 틀린 해석이었다 —
기계어는 같았고 주소가 달랐다.
