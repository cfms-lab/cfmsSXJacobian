## 왜

엔진 main(92d8838)의 CPU 기본이 생성 커널이 됐다 — 굽힘 `gn_state`, 인장 · Provot 전단 생성 커널(`docs/GATE_LINK_L3.md` 「판정 뒤」).
이 리포의 게이트(L0 – L4R)는 노드 25 의 작은 천과 평평한 천 두 장면만 봤다. 엔진 리포에는 합성 장면 시험이 따로 있다
(`drape/scripts/py_*_test.py` 44 개 · `test_*.py` 2 개 — 바디 접촉 · 봉제 · 자기충돌 · 재질 · PCG · 생애 주기 등). 새 기본값으로는
아직 한 번도 돌리지 않았다(엔진 `CLAUDE.md` 「현재 상태」의 「아직 안 한 것」).

묻는 것은 둘이다. 새 기본값 때문에 실패하게 된 시험이 있는가. 킬스위치(`CFMS_CPU_SXJ_BEND=off` + `CFMS_CPU_SXJ_MEMBRANE=off`)가
이 시험들에서도 종전 엔진과 같은가.

## 방법

- **팔 셋.** N = 엔진 92d8838 DLL, 환경 변수 없음(새 기본값). K = 같은 DLL + 킬스위치 둘. B = 엔진 378d20c DLL(종전).
  DLL 은 `%TEMP%\cfmsDrape_build_sxjlink`(92d8838) 와 `%TEMP%\cfmsDrape_build_378d20c`(기준 워크트리에서 빌드)의 것이다.
- **시험 트리는 엔진 리포 밖에 둔다.** `git archive 92d8838 drape` 를 `%TEMP%\cfmsSXJ_engine_suite\<팔>\` 에 풀어 팔마다 한 벌씩 쓴다.
  시험 스크립트 · 래퍼(`drape/scripts` · `drape/cfmsdrape`)는 378d20c 와 92d8838 에서 같다(전제). 래퍼의 기본 후보 자리
  `drape/build/0.2.2/Release/cfmsDrape.dll` 에 그 팔의 DLL 을 놓는다 — 시험이 `Drape()` 로 열든 `backend="cpu"` 로 열든 그 DLL 을 읽는다.
  `CFMS_DRAPE_DLL` 은 주지 않는다. GPU DLL 은 두지 않는다. 엔진 리포(main · 브랜치 · 기준 워크트리)는 읽기만 한다.
- **실행.** 엔진의 가상 환경 python(`cfmsDrape_dev\drape\.venv`), 작업 폴더 = 사본의 `drape`. `py_*_test.py` 는 인자 없이 부른다
  (엔진의 10 차 검증 기록 `docs/validation/cfmsDrape_0.2.2_predist_20261019.json` 과 같게 — `py_velocity_readback_test.py` 만
  `--backend cpu`). `test_*.py` 는 `-m pytest … -q`. 시험마다 세 팔을 동시에 띄우고, 시험은 이름 순서로 하나씩 돌린다.
- **제한 시간 900 s**(10 차 검증 기록과 같다). 넘으면 프로세스 트리를 죽이고 「제한 시간」으로 적는다.
- **스레드 · 그 밖의 환경은 건드리지 않는다.** 많은 시험이 스스로 `OMP_NUM_THREADS=1` 을 둔다(`setdefault`). 하네스는
  `OMP_NUM_THREADS` · `CFMS_OMP_THREADS` · `CFMS_DRAPE_DLL` · `CFMS_CPU_SXJ_*` 를 자식 환경에서 지우고(K 만 킬스위치 둘을 넣는다),
  `PYTHONUTF8=1` · `PYTHONDONTWRITEBYTECODE=1` 만 더한다. 세 팔의 환경은 킬스위치 말고는 같다.
- 종료 상태 = 종료 코드, 또는 「제한 시간」. 통과 = 종료 코드 0.

**PASS** = S0 · S1 · S2 모두. S2 가 미달이면 FAIL 이고, 걸린 시험마다 까닭을 찾아 적는다 — 시험이 종전 수치에 묶여 있는 것인지,
새 기본값의 실제 결함인지. 기본값을 되돌릴지 · 시험을 고칠지 · 그대로 둘지는 사용자 몫이다.

**제한 시간 규칙(미리 정함).** 세 팔을 함께 돌리면 스레드를 정하지 않은 시험은 서로 느려진다. 그래서 어느 팔이든 제한 시간에 걸린
시험은 본 실행이 끝난 뒤 **세 팔을 하나씩(동시에 돌리지 않고) 다시 돌려 그 결과로 판정한다.** 다시 돌려도 세 팔이 모두 제한 시간이면
「판정 불가(시간)」로 적고 S1 · S2 에서 뺀다(엔진 기록에 `py_open_shell_contact_test` 가 900 s 를 넘는 기존 실패로 올라 있다).

**보고만**:

- 세 팔 모두 같은 꼴로 실패한 시험 — 엔진 기록의 기존 실패(엔진 `CLAUDE.md` 「현재 상태」 · 10 차 검증 기록)와 대조하고, GPU DLL 이나
  인자가 없어서 실패한 것은 따로 적는다(범위 밖).
- N 만 통과한 시험(K · B 는 실패).
- K 와 B 의 표준 출력이 바이트까지 같은 시험 수(시간을 찍는 시험은 다를 수 있어 판정에 쓰지 않는다).
- N 의 표준 출력이 K 와 다른 시험 수, 시험마다 걸린 시간.

규칙을 이렇게 정한 이유:

- **K 를 기준 팔로 쓴다**: 같은 DLL · 같은 래퍼에서 스위치만 다르므로 N 과의 차이가 기본값 탓임이 분명하다. B 는 「킬스위치 = 종전
  엔진」을 이 시험들에서도 확인하려고 둔다(L2-1 · L3-1 은 작은 천에서만 봤다).
- **종료 코드로만 판정한다**: 시험마다 통과 기준이 그 안에 있다. 새 기본값은 수치를 바꾸므로(굽힘 J) 출력이 같을 수 없다 — 묻는 것은
  시험이 정한 기준을 여전히 넘는가다.
- **기존 실패는 막지 않는다**: 엔진의 10 차 검증과 같은 처리다. K 에서 실패하는 시험은 새 기본값과 무관하다.

**1. 병렬 PCG 의 gather 가 생성 굽힘 경로의 직렬 곱과 비트가 다르다 (S2 의 둘) — 실제 결함, 까닭 확인.**

  되풀이해야 비트가 같은데, 그때 V 목록만 새 꼴에 맞추고 **J 목록은 옛 꼴(목록 종류 2)로 남겼다.** 그래서 마지막 비트가 다르다.

  `bTransposeAwareJOnly` 가 거짓이다.
- 뜻: 엔진 불변식 「CPU 동역학 PCG 가 기본으로 병렬 — 위치는 비트 동일」(2026-10-20)이 새 기본값에서 깨진다. 곱 하나의 차이는
